# 8x8x8 LED Cube — Device & Logic Contract

This file is the **source of truth for the intended real-world behavior of the device**.

The device behavior has priority. The Arduino code, physical wiring, Bluetooth HM-10 communication, and web app are implementations of these behaviors.

**Analysis does not equal permission to modify.** Before changing any project file, analyze the current code first and modify only the file(s) the user explicitly authorizes. A rule written here is a requirement, not permission to implement or change it.

## 1. Device behavior — highest priority

| Device / user action | Expected real-world behavior |
|---|---|
| Arduino power-up | The cube waits 3 seconds for the power supply / capacitors to charge, then starts displaying the built-in animations in Auto Mode. |
| Normal operation after startup | The cube automatically cycles through the built-in animations while in Auto Mode. |
| User holds touchpad for more than 3 seconds | The cube switches between Auto Mode and Manual Mode. The currently selected animation is kept when changing mode. |
| User gives a single short touch | While in Manual Mode, the cube advances to the next built-in animation. A short touch does not switch modes by itself. |
| User touches while Bluetooth is connected | Physical touch control is ignored while the web app is connected and controlling the cube. |
| Bluetooth is disconnected | After the configured disconnect detection/debounce period, the cube independently returns to built-in Auto Mode. The web app does not need to send an Auto command. |
| Brightness control with Bluetooth disconnected | The physical potentiometer controls the cube brightness. |
| Brightness control with Bluetooth connected | The web app brightness control sets the cube brightness. |
| Bluetooth connection | The web app connects to the HM-10, completes the connection handshake, and then enables the available controls. |
| Web Auto control | The cube switches to built-in Auto Mode. |
| Web Manual control | The cube switches to Manual Mode and keeps the current animation. |
| Web Next Animation control | The cube advances to the next built-in animation. |
| Web Math control | The web app sends the math expression to the Arduino, then the Arduino renders that expression on the cube. |
| Web Custom control | The web app sends the custom function to the Arduino, then the Arduino renders that function on the cube. Stopping Custom returns the cube to Auto Mode. |
| Front face | The physical front face is the reference face for left-to-right X position and for anything described as being seen from the front. |
| Rotating heart | The heart is a normal built-in animation and must appear on the physical front face using the same built-in animation system as the other animations. |

## 2. Physical device / wiring contract

| Part / connection | Required behavior |
|---|---|
| Arduino | Controls the cube, reads the physical controls, manages the HM-10, and performs Math/Custom rendering locally. |
| 74HC595 chain | Receives only actual LED display data generated by the Arduino display system. |
| Touchpad input | Physical touchpad is the local mode/animation control described in the Device Behavior table. |
| Potentiometer | Physical brightness control when Bluetooth is disconnected. |
| HM-10 | Provides the wireless connection between the cube and the web app. |
| HM-10 state signal | Lets the Arduino detect a real Bluetooth disconnect independently of the web app. |
| Physical front face | Columns 1–8 run left to right when viewed from the front. This orientation must remain consistent in animations and previews. |

Current Arduino interface pins:

| Function | Arduino pin |
|---|---|
| Touchpad | D10 |
| 74HC595 data | D11 |
| 74HC595 clock | D13 |
| 74HC595 latch | D12 |
| HM-10 state | D2 |
| Brightness potentiometer | A0 |

These physical connections are part of the device behavior and must not be casually reassigned because the code, wiring, and hardware all depend on them.

## 3. Modes and animation behavior

| Mode | Device behavior |
|---|---|
| Auto Mode | Built-in animations run automatically and move to the next animation on the normal carousel timing. |
| Manual Mode | The selected built-in animation continues running until the user or web app selects the next animation. |
| Math Mode | The Arduino evaluates the uploaded math expression and displays the result on the cube. |
| Custom Mode | The Arduino evaluates the uploaded custom function and displays the result on the cube. |
| Return to Auto | Bluetooth disconnect or stopping Custom returns the cube to built-in Auto Mode. |

## 4. Bluetooth / web app behavior

The web app and Arduino communicate through the HM-10 using command messages and acknowledgements.

| Web action | Arduino response / behavior |
|---|---|
| Connect | Establish HM-10 connection and complete handshake before normal controls are enabled. |
| Handshake | Web app sends `H`; Arduino replies `HANDSHAKE_OK`. |
| Auto | `A` selects Auto Mode and Arduino confirms with `MODE_AUTO`. |
| Manual | `M` selects Manual Mode and Arduino confirms with `MODE_MANUAL`. |
| Next | `N` advances the animation when used in Manual Mode and Arduino confirms with `ANIMATION_NEXT`. |
| Math upload | Web app starts the upload channel, sends the expression, and waits for the Arduino result. |
| Start Math | `F` starts Math Mode after a valid math program exists. |
| Custom upload | Web app starts the upload channel, sends the custom function, and waits for the Arduino result. |
| Start Custom | `X` starts Custom Mode after a valid custom function exists. |
| Stop Custom | `S` stops Custom Mode and returns the cube to Auto Mode. |
| Brightness | `B` followed by the brightness value sets the Arduino brightness while connected. |

## 5. Bluetooth reliability rules

| Rule | Required behavior |
|---|---|
| Handshake timing | Notifications are enabled before the first handshake is sent. |
| Handshake reliability | A missed first response must not cause an unnecessary connection failure; handshake retry is supported. |
| BLE writes | Transient Bluetooth write-busy conditions may be retried. |
| Incoming data | Notifications are treated as a text stream so a message split across packets is still handled correctly. |
| ACK ordering | For a command expecting an acknowledgement, the web app prepares the acknowledgement waiter before sending the command. |

## 6. Frame, coordinate, and display behavior

| Rule | Required behavior |
|---|---|
| Coordinates | X = left-to-right columns on the physical front face; Y = front-to-rear depth; Z = bottom-to-top height. |
| Front face | `y=0` is the physical front face and must remain the reference for front-view behavior. |
| Animation generation | Built-in, Math, and Custom animations produce cube frame data through the common display system. |
| Display buffer | Animation logic updates the display buffer; the refresh system handles sending display data to the 74HC595 chain. |
| Protocol bytes | Bluetooth control commands are control messages only; they are never treated as LED frame data. |
| Rotating heart | Uses the same built-in animation pipeline as the other built-in animations. |

## 7. Memory behavior

The Arduino is RAM-limited. The implementation should keep the intended behavior while avoiding unnecessary memory use.

Preferred approach:

**Calculate the current animation state → build one frame → copy it to the display buffer → refresh the cube.**

Do not replace function-based animation logic with large stored frame tables unless there is a clear reason.

Important existing RAM structures include `displayBuffer`, the packed math program, and the Bluetooth receive buffer.

## 8. Code-change protection

When working on this project:

- Read this document before changing the Arduino or web app.
- Treat the **Device behavior** section as the highest-priority requirement.
- Compare the requested change against the real-world behavior before editing code.
- Preserve wiring, pin assignments, front-face orientation, touch behavior, brightness behavior, Bluetooth behavior, and mode behavior unless the user explicitly asks to change them.
- Never change a file just because an analysis finds something that could be improved.
- **Analyze/check/report means no code modification.**
- Modify only the file(s) explicitly authorized by the user.
- If the requested behavior already exists, report that instead of rewriting the implementation.

## Golden rule

**The code must serve the device behavior, not redefine it accidentally.**

When a code change is proposed, verify that the physical cube still behaves exactly as described in the Device Behavior table unless the user intentionally requested a behavior change.
